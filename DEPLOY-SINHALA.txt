06. Spam controls සහ optional CAPTCHA

Default controls server එකේ enforce වෙනවා, browser validation පමණක් නොවේ:
  • exact @sltc.ac.lk domain; no subdomains or mail header/formula injection
  • consent + honeypot + server-signed form timestamp
  • same email: 10-minute resend cooldown; maximum 3 verification emails/day
  • whole app: maximum 20 verification emails/day; 300 accepted attempts/day
  • at least 40 remaining mail recipients required before verification send
  • private hashed verification token, expires in 30 minutes, single use
  • 1000 pending+confirmed records; default 200 confirmed cap
  • ScriptLock serialises signup mutations and durable quota counters
  • no public subscriber list, count, recipient dump, or admin RPC

Daily abuse counters use Asia/Colombo calendar dates. Google email quota
resets on Google's own 24-hour window; these are DIFFERENT windows.
Form proof is not a CAPTCHA and is not single-use; humans/bots can fetch
another form. Determined attackers can consume the small global budget or
cause up to the capped number of unwanted verification emails. Google Apps
Script does not supply a dependable client IP in doGet's documented event,
so this code does not pretend to enforce IP limits or DDoS protection.
Global caps protect mail spend/quota but can temporarily deny valid signup.
If attacked: SIGNUPS_ENABLED=false, inspect privately, enable CAPTCHA,
then reopen. Unsubscribe remains available while signups are paused.

Optional Cloudflare Turnstile (recommended before widely sharing publicly):
1) Create a free Managed widget in Cloudflare Turnstile dashboard.
2) Apps Script HTMLService runs inside a Google-hosted iframe. The actual
   iframe hostname may differ from script.google.com. Use browser DevTools
   to identify the rendered iframe hostname and register that exact hostname
   if Cloudflare allows it. Do not assume a fixed hostname or use a wildcard
   Google domain. If hostname/iframe restrictions prevent reliable operation,
   keep the conservative default or use dedicated hosting for stronger abuse
   protection. This integration has not been tested in a live Google iframe.
3) Set ALL these signup Script Properties:
     TURNSTILE_SITE_KEY   = public site key

08. Privacy / unsubscribe / retention

Only confirmed rows are recipients. Every alert has its own signed unsubscribe
link. Opening it and pressing Unsubscribe deletes that subscriber row. A later
signup creates a new ID and needs confirmation again. Queued mail referencing
an old deleted ID is skipped.

Pending records older than24h since last request are deleted by the daily
cleanup trigger (normally within48h; outages can delay cleanup). Confirmed
records last until unsubscribe/service closure. Consent version + timestamps
record the opt-in. Sheet version history, delivered mail, provider logs and
backups may retain copies under Google's policies. Do not promise instant
deletion from every provider backup. Restrict editors and avoid PII logging.

If someone loses the unsubscribe link, organiser verifies the request and
deletes ONLY that person's row privately. Do not publish emails to identify
students. At shutdown: disable new signups, stop subscriber sends, delete
subscriber records/queue as appropriate and archive public deployment.

09. Token/security rotation

LMS_AUTHTOKEN is DIFFERENT from SIGNING_SECRET and confirmation link tokens.
  • LMS_AUTHTOKEN: private LMS calendar access; monitor project only.
  • SIGNING_SECRET: HMAC signing key shared by these TWO private projects.
  • Email link tokens: limited verification/unsubscribe capabilities.

If old chat/code/screenshots contained an actual LMS token or private ICS URL,
treat it as exposed. In LMS, regenerate/revoke the calendar export token if
the LMS supports it; otherwise ask the LMS administrator to revoke it. Menu
names depend on SLTC's LMS version. Changing password alone may not revoke
a calendar export token. Confirm that the OLD URL no longer returns private
events; do not post old/new token here. Update monitor property, test one
private fetch without logging URL/body/token, then continue the same trigger.
Never proxy that feed publicly, log fetch errors containing the URL, or put
the feed URL in HTML/email/assets/source control. Script Properties hide
secrets from students but trusted project editors can still read them; they
are not a separate encrypted vault against editors.

SIGNING_SECRET rotation after suspected exposure:
1) Pause signups and temporarily pause the monitor trigger while recording
   its existing handler/frequency (no new duplicate trigger).
2) Put a new CSPRNG-generated64+ character secret in BOTH projects.
3) Delete all pending rows to revoke outstanding confirmation tokens.
   Their verification hashes alone would still validate until expiration;
   changing signing key alone does NOT revoke already-issued confirm links.
4) Confirmed rows can stay. Old unsubscribe links stop validating. Future
   mail signs fresh links with the new secret. Offer private manual removal
   for students whose only copy is an old link.
5) Resume same trigger and signups after testing. If project editors were
   compromised, remove access and review Sheet, source and deployments too.

Routine secret rotations should be planned: do not silently break old
unsubscribe links unnecessarily. Optional TURNSTILE_SECRET_KEY rotation is
separate; change it in Cloudflare and signup properties, then test.
